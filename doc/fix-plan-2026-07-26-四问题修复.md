## 问题 1：run_async 线程池饿死风险（原描述部分不准确，已核实）

### 现状核实

- `core/async_utils.py:14`：模块级单例 `_EXECUTOR = ThreadPoolExecutor(max_workers=4)`。
- `core/async_utils.py:26-43`：`run_async` 在"已有事件循环"时，向该 4 线程池提交
  `asyncio.run(_body())`——worker 线程内**新建独立事件循环**跑协程，调用线程阻塞在
  `future.result(timeout=60)`。
- Web 路径：`web/server.py:189,478` 用 `loop.run_in_executor(None, ...)`（默认执行器，
  约 32 线程）跑同步 `process_message` → `MessageHandler.handle_message` →
  `run_async`（如 `core/message_handler.py:179`、`core/cognitive_state.py:68`）。
  **主事件循环不会被阻塞**，这一层是安全的。
- `memory/memory_agent.py:241,261,282,296`：协程内部用 `loop.run_in_executor(None, ...)`
  卸载同步 LLM/embedding 调用，**没有**嵌套调用 `run_async`——目前未发现实际的嵌套路径。

### 真正的风险（与原描述的区别）

原描述说"新事件循环与主循环冲突"——不准确，worker 内的新循环是标准做法且已被
生产路径长期使用。真正的风险是**线程池饿死**：`run_async` 只在"检测到有运行中的
循环"时才走线程池，而 worker 线程里的新循环也算"运行中的循环"——如果将来某个协程
（在 worker 的新循环里）再调用一个内部走 `run_async` 的同步函数（如
`memory/long_term.py:105-108` 的同步包装），就会**再向同一个 4 线程池提交任务并阻塞
当前 worker**。4 个 worker 同时处于这种状态即互相等待。因 `future.result(timeout=60)`
兜底，表现为 60 秒级卡顿而非永久死锁，但属于隐患。

### 修复方案

1. **重入防护（fail-fast）**：`core/async_utils.py` 增加 thread-local 标记。
   `run_async` 在 worker 分支入口设置标记；若发现标记已存在（即嵌套调用），
   记 error 日志并抛出 `RuntimeError("nested run_async call")`，把未来的嵌套
   从"60 秒卡顿"变成"立刻报错可定位"。
2. **调用路径审计（测试固化）**：新增测试遍历 `memory/long_term.py` 全部同步
   包装方法，断言它们不被任何协程调用——可行的简化做法：在 `run_async` 中加
   标记后，跑现有全套测试即隐含覆盖（现有测试会触发真实路径）；再加一个直接
   单测：在嵌套场景下断言抛 `RuntimeError`。
3. `runtime_driver.py:_run_blocking`（`core/runtime_driver.py:170-173`）保持
   `run_in_executor(None, ...)` 不变——它走的是默认执行器，无饿死问题。
   **不要**把它改成 `run_async`。

### 验收

- 新增嵌套调用单测通过；全套测试不红（基线 843 passed）。

## 问题 2：CognitiveState 一致性（属实，三处具体问题）

### 现状核实（`core/message_handler.py`、`core/inner_drive.py`）

1. **状态在决策后被改写**：`message_handler.py:313-314`
   `state.memory_summary = drive_result.context_summary or state.memory_summary`。
   Agent 1 在 `assess`（`inner_drive.py:299-315`）里消费的是改写前的摘要，
   Agent 3 消费的是改写后的——同一字段两种含义，违反快照语义。
2. **轻量渲染逻辑重复**：`inner_drive.py:304-309` 与 `message_handler.py:607-612`
   各写了一遍 `ContextBuilder().build("agent3", ma)` 的 fallback 逻辑，已出现漂移风险。
3. **冗余再检索**：`message_handler.py:616-623`：即使 `memory_summary` 已有值，
   仍可能调用 `a.retriever.retrieve_for_query(user_input)` 构造 `mem_ctx`
   （当 `a.current_memory_context` 为 None 时）。而 `build_system_prompt` 在
   `memory_context_summary` 非空时根本不用 `mem_ctx`（`prompts/system.py:818-834`），
   这次检索是纯浪费。

### 修复方案

1. **状态只写一次**：删掉 `message_handler.py:313-314` 对 `state.memory_summary` /
   `memory_confidence` 的改写。Agent 3 需要的"评估后摘要"通过 `drive_result.context_summary`
   传递——`_run_agent3` 已有的 fallback（`message_handler.py:613-614`）天然覆盖：
   把 `state.memory_summary` 的读取逻辑改为：
   - `state.memory_answer` 非空 → 轻量 profile 渲染（逻辑 2 统一后的 helper）；
   - 否则 `drive_result.context_summary` 非空 → 用它；
   - 否则 `state.memory_summary`。
2. **统一渲染 helper**：在 `core/cognitive_state.py`（或 `memory/retrieval_pipeline.py`）
   增加一个函数，如 `render_light(ma, fallback: str) -> str`，封装
   `ContextBuilder().build("agent3", ma)` + 空值回退；`inner_drive.py:304-309` 与
   `message_handler.py:607-612` 都改为调用它。
3. **去掉冗余检索**：`message_handler.py:616-623` 改为：
   `memory_summary` 非空时 `mem_ctx = a.current_memory_context`（可为 None，
   `build_system_prompt` 该分支不用它）；仅在 `memory_summary` 为空时才
   `retrieve_for_query`。
4. 注释更新：`CognitiveState` docstring 与 WS-25 注释改为"装配后不再修改"的明确约定。

### 验收

- 现有 `tests/test_cognitive_state.py` 及全套测试不红；
- 新增单测：同一轮内 Agent 1 看到的摘要与 Agent 3 摘要来源一致（memory_answer
  路径走轻量渲染、retriever 路径不二次检索，可用 mock retriever 计数断言）。

## 问题 3：inner_drive_state 淘汰策略（**已修复，无需改代码，只补测试**）

### 现状核实

`core/inner_drive_state.py:292-304`（`_evict_if_needed`）当前实现已是：
先清非活跃（resolved/expired/decayed，最旧的优先），活跃条目按
`min(entries, key=lambda e: (e.priority, e.created_at))` 淘汰——**低 priority 先走，
同 priority 时最旧的先走**。这正是原建议的"分数淘汰"，docstring 注明"二期，非 FIFO"。
原描述（"FIFO 淘汰最旧活跃条目"）已过时。

### 修复方案

- 不改实现。在 `tests/` 找到该模块现有测试文件（检索 `inner_drive_state`）补充用例：
  1. 容量满时优先淘汰非活跃条目；
  2. 全活跃时淘汰 priority 最低者（而非最旧者）；
  3. priority 相同时淘汰 created_at 最旧者。

### 验收

- 新测试通过；全套测试不红。

## 问题 4：多请求工具结果无法归因（属实）

### 现状核实

- `core/tool_agent.py:18-26`：`ToolCallRecord` 只有
  `name/arguments/success/output/elapsed_ms/error_type/retryable`，**没有**所属请求字段。
- `core/tool_agent.py:269-280`：`run_with_requests` 多请求并发后直接
  `merged.records.extend(single.records)`——合并后丢失"哪条记录属于哪个请求"。
- `core/tool_agent.py:285-305`（`format_for_phase2`）→ `core/dispatcher.py:351-385`
  （`format_tool_results`）：逐条渲染 `<tool_result name="...">` 块，无请求归属信息。
  请求 2 成功、请求 1 失败时，Agent 3 无法向用户说清"哪件事没办成"。

### 修复方案

1. `ToolCallRecord` 增加字段 `request: str = ""`（放最后，带默认值，不破坏现有构造）。
2. 找到 `run_with_request` 内部创建 `ToolCallRecord` 的位置（`core/tool_agent.py` 内
   `run` / 记录收集处），把当前请求的原始文本填入 `request`（超长截断到 ~80 字符）。
   单请求路径 `run_with_request(user_input)` 同样填。
3. `format_for_phase2`：当 `result.records` 中存在两个及以上**不同**的 `request` 值时，
   按 request 分组渲染，每组前加一行小标题，如 `【请求：搜索最近的 AI 新闻】`；
   单请求时保持现有格式不变（避免 prompt 膨胀）。铁律段（`dispatcher.py:380-384`）
   原样保留。
4. `ToolExecutionResult.from_records`（`core/message_handler.py` 顶部附近定义）
   如需感知分组，最小改动即可——优先保持其签名不变。

### 验收

- 新增单测：两个请求（一成一败）合并后，`format_for_phase2` 输出包含两个请求
  小标题且成功/失败归属正确；单请求输出与旧格式一致。
- 全套测试不红。
