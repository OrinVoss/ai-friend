# 全项目代码审查：修复 13 个 bug（issue #306-#319）

**时间**：2026-08-18

**背景**：对全项目约 3 万行代码做并行分模块审查（测试套件 871 项全绿，故以下均为测试未覆盖的潜伏 bug）。14 项"较大及以上"发现已建 issue #306-#319，本次修复其中 13 项；#311 的重复 turn_number 竞态通过整交换互斥修复，#312 事件循环冻结一并修复。

## 严重（5 项）

### #306 SessionManager 自死锁
`web/session.py` — `get_or_create` 持有非递归 `threading.Lock` 时调用 `cleanup_old()`（后者再次取锁），每创建第 10 个 session 必死锁。修复：锁内只置 `need_cleanup` 标记，`cleanup_old()` 挪到锁外。

### #307 工具超时反致永久挂起
`core/dispatcher.py` — `with ThreadPoolExecutor` 超时退出时 `shutdown(wait=True)` 无限等待卡死的工具线程。修复：不再用 `with`；超时分支 `future.cancel()` + `shutdown(wait=False)`。

### #308 WS token 鉴权绕过
`web/server.py` — 此前仅 init 帧校验 token，跳过 init 直接发 message 即可使用 default session。修复：连接级 `ws_authed` 状态，token 启用时非 init 帧一律 4001 关闭。

### #309 路径穿越
`session_id`/`role_id` 原样拼路径，可任意写 `.json`/探测文件。修复三层：
- `utils/__init__.py` 新增 `is_valid_session_id`（白名单字符集，1-64 长）；
- `web/schemas.py` `ChatRequest.session_id` 加 `pattern` 校验（REST 422）；
- `web/session.py` `get_or_create` 入口校验（覆盖 WS）；`core/personality_manager.py` 四个路径方法纵深校验。

### #310 记忆合并吞错丢事实
`memory/consolidation.py` — `_call_llm` 失败返回 `""` 被当成"无事实"，`_extract_facts` 吞异常导致 pending buffer 被误清空、事实永久丢失。修复：`_call_llm` 失败返回 `None`（区别于空内容）；`_extract_facts` 失败抛 `RuntimeError` 使 `consolidate` 保留 buffer 下批重试；`_verify_contradiction_llm` 对 `None` 容错。

## 审查后排除的误报

- glob 工具 Windows 路径分隔符不匹配 —— 实测 `fnmatch` 在 Windows 会 normcase 统一分隔符，不存在该问题。
- `web_fetch` SSRF 可被 DNS 绕过 —— 实际抓取由远端 AnySearch API 执行，本机无 SSRF 面。
- `expire_due_insights` 时间格式比较错误 —— 当前无调用方传 `expires_at`，死代码路径，暂不修。

## 追加：#305 CLI 启动即崩溃（2026-08-18 运行时确认）

`ui/cli.py` — `main()` 是 async（`await db.open()`），同步 CLI 主循环在已运行的事件循环线程里调 prompt_toolkit 的同步 `prompt()`，其内部 `asyncio.run()` 不能嵌套 → `RuntimeError: asyncio.run() cannot be called from a running event loop`。修复：`read_input` 检测调用线程已有运行中循环时，把 `session.prompt()` 放到无循环的专用线程执行（worker 内 `asyncio.run` 合法），`patch_stdout` 行为不变。冒烟验证：循环线程/无循环线程两条路径均读出输入。

## 追加二：embedding 服务端口不一致（2026-08-18 运行时确认）

`config.json` 的 `embedding_endpoint` 为 18080，但 `start_embedding_server.bat` 硬编码 `--port 8080`；`_start_llama_server` 发现 bat 即用 bat（H-04 端口跟随只在 exe 兜底路径生效）→ 服务起在 8080、应用连 18080，自检 30s 失败降级关键词检索。修复：bat 端口改由 `%1` 传入（缺省 8080），`core/embedding_server.py` 调 bat 时传 `_port_from_endpoint(endpoint)`。已用应用同款 `Popen([bat, "18080"])` 重启验证：`/health` 200、`/v1/embeddings` 返回真实向量。

**教训**：.bat 必须是 CRLF 行尾。首版修复用 LF 写出 bat 后，cmd 解析错乱（日志出现 `'t' 不是内部或外部命令`），`set PORT=%1` 未生效、始终回落 8080——参数其实传到了，被行尾问题吞掉。已用 printf 以 CRLF 重写。

同批小修（#310 后续日志噪音）：`_call_llm` 返回 `None` 后，`analyze_sentiment`/`_summarize_experience`/L1 insight 三处补显式判空，避免 `None.strip()` 的 AttributeError 掩盖真实失败原因（如 402）。

## 追加三：三项优先改进（2026-08-18，来自外部评审建议）

### 改进1：consolidation 幂等（🔴）
`memory/consolidation.py` — #310 修复后 facts 失败会保留 buffer 重试，但每次重试都无条件新建 Observation，同批对话堆积重复观察。修复：新增 `_last_obs_sig`/`_last_obs_id` 签名缓存 `(start_id, end_id, len, hash(turn_text))`，同批重试复用已有 observation；签名含 turn_id，新批次必然创建新观察。

### 改进2：FACT 接地后处理校验（🔴）
`memory/consolidation.py` — prompt 早已要求"只提取用户亲口说的事实"但 LLM 仍会推断。新增不依赖 LLM 的确定性校验：`_user_utterances` 抽取 "用户:" 行，`_grounded_in_user_text` 对每条事实的值做接地检查（子串命中或 2-gram 覆盖率 ≥ 0.5），不接地即丢弃并 INFO 记日志。`_extract_facts` 与统一调用路径均传入 `source_text`；未传则不校验（兼容旧调用）。7 个既有测试的夹具改为生产形状输入（"用户: " 前缀 / mock 事实值落在用户话语中）。

### 改进3：inner_drive reasoning 详细化（🟡）
`core/inner_drive.py` — 两处 JSON schema 的 reasoning 描述改为要求 2-4 句详细决策依据（触发判断、考虑过的选项、排除原因）；决策日志不再截断（`reason[:60/80]` → 全文，存储上限 300 字不变），边界情况可追踪。
